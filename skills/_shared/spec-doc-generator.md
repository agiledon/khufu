# Spec Doc Generator — Post-Generation Spec Documentation

Shared module for generating and updating execution record spec documents after tests have been generated, compiled, and executed. This creates a persistent, versioned record of what tests exist, their results, and coverage data.

## Core Principle

**Every test generation run produces a spec document.** This document is the authoritative record of what was generated, when, and with what results. It enables incremental generation (dedup on subsequent runs) and provides traceability over time.

## Workflow

### Step 0: Ensure Directory Structure (MANDATORY — Run First)

**BEFORE any file reading or writing**, ensure the required directories exist.

Read `khufu.yaml` → `spec.docsDirectory` (default: `docs/khufu/`).

Use **Bash** to create only the directories needed for the **current test layer**:

```bash
mkdir -p <docsDirectory>/<layer>
```

Example for UT layer with default config:
```bash
mkdir -p docs/khufu/ut
```

**Only create the subdirectory for the current layer** (ut/, it/, api/, or e2e/). Do NOT create subdirectories for other test types — they will be created when those test types run.

**This step MUST be executed even if the directory appears to exist** — `mkdir -p` is idempotent and safe.

### Step 1: Collect Data

After test compilation and execution (Steps 10-A and 10-B in each SKILL.md), collect:

1. **Test execution results**: From the test run output — which tests passed/failed/skipped
2. **Coverage data**: From the coverage tool — overall and per-class line/branch/function coverage
3. **Test metadata**: Framework name + version, coverage tool name + version, execution time
4. **Test case details**: For each generated test — test class, test method, target class, target method, status

### Step 2: Determine Spec Doc Path

Read `khufu.yaml` → `spec.docsDirectory` (default: `docs/khufu/`).

The spec doc path is:
```
<docsDirectory>/<layer>/<YYYY-MM-DD>-<layer>-test-cases.md
```

Examples:
- `docs/khufu/ut/2026-07-13-ut-test-cases.md`
- `docs/khufu/api/2026-07-13-api-test-cases.md`
- `docs/khufu/e2e/2026-07-13-e2e-test-cases.md`

Get today's date in `YYYY-MM-DD` format using the `date` command:
```bash
date +%Y-%m-%d
```

### Step 3: Check for Existing Spec Doc

Use **Read** to check if the spec doc file already exists.

**If the file EXISTS** (same date, same layer):
1. Read the existing file
2. Parse the YAML frontmatter → extract `version`
3. Increment version: `newVersion = oldVersion + 1`
4. Parse the existing Test Cases table
5. Merge: keep existing test cases + add new ones (dedup by Test Class + Test Method)
6. Recalculate Summary statistics
7. Update Coverage Statistics with latest data

**If the file does NOT exist** (first run today for this layer):
1. Create with `version: 1`
2. Populate with all generated test cases

### Step 4: Build the Spec Document

Use the following template. Write with **Write** tool.

```markdown
---
version: <N>
created: <YYYY-MM-DD>
updated: <ISO-8601 timestamp>
testType: <ut|it|api|e2e>
language: <detected language>
tool: <framework name> <version>
coverageTool: <tool name> <version>
---

# <Test Type> Test Cases — <YYYY-MM-DD>

## Summary

| Metric | Value |
|--------|-------|
| Total test cases | <N> |
| Passed | <N> |
| Failed | <N> |
| Skipped | <N> |
| Test tool | <framework name> <version> |
| Coverage tool | <tool name> <version> |
| Language | <language> |
| Execution time | <duration>s |

## Test Cases

| # | Test Class | Test Method | Target Class | Target Method | Status |
|---|-----------|------------|-------------|--------------|--------|
| 1 | `UserServiceTest` | `ShouldCreateUserWhenValidInputGiven` | `UserService` | `createUser` | ✅ |
| 2 | `UserServiceTest` | `ShouldThrowExceptionWhenEmailDuplicate` | `UserService` | `createUser` | ✅ |
| 3 | `OrderServiceTest` | `ShouldCalculateTotalCorrectly` | `OrderService` | `calculateTotal` | ❌ |
| ... | ... | ... | ... | ... | ... |

### Overall

| Metric | Value |
|--------|-------|

- **Generated by:** khufu-<layer> v<version>

- **Timestamp:** <ISO-8601>

- **Fragile tests:** <N> (if applicable)
```

### Step 5: Write the Spec Doc

Use **Bash** to ensure the target layer directory exists (idempotent, safe to run even if it exists):
```bash
mkdir -p <docsDirectory>/<layer>/
```

Then use **Write** to create or overwrite the spec doc file at:
```
<docsDirectory>/<layer>/<YYYY-MM-DD>-<layer>-test-cases.md
```

**CRITICAL**: The `mkdir -p` command MUST run before the **Write** call. The Write tool does not auto-create parent directories.

### Step 6: Update the Wizard File (test-cases.md)

The wizard file at `<docsDirectory>/test-cases.md` serves as the index of all spec docs.

#### 6.0 Ensure Wizard Directory Exists

**MANDATORY**: Before reading or writing the wizard file, ensure the directory exists:
```bash
mkdir -p <docsDirectory>
```

#### 6.1 Check if wizard exists

Read `<docsDirectory>/test-cases.md`. If the Read fails (file not found), treat it as "wizard does NOT exist" (Step 6.3).

#### 6.2 If wizard EXISTS:

1. Parse the YAML frontmatter → extract `version`
2. Increment version: `newVersion = oldVersion + 1`
3. Update `updated` timestamp
4. In the "Recent Generations" table:
   - **If a row for today's date + current layer exists**: Update the Tests/Passed/Failed counts for that row only
   - **If no row exists**: Insert a new row at the top for the current layer only
   - **Do NOT modify rows for other test types or dates** — they remain as-is
5. In the "Coverage Overview" table:
   - Update or insert the row for the current layer + date
   - **Do NOT modify rows for other test types**
6. Write the updated wizard file

#### 6.3 If wizard does NOT exist:

Create it with `version: 1`. **Only include the current layer** in the tables — do NOT pre-populate rows for layers that have not run:

```markdown
---
version: 1
created: <YYYY-MM-DD>
updated: <ISO-8601 timestamp>
---

# Khufu Test Cases Index

This file is the master index of all test case specification documents generated by khufu. Each linked document contains detailed test case listings, coverage statistics, and execution results for a specific date and test type.

## Recent Generations

| Date | Type | File | Tests | Passed | Failed |
|------|------|------|-------|--------|--------|
| <YYYY-MM-DD> | <UT> | [<filename>.md](<layer>/<filename>.md) | <N> | <N> | <N> |

## Coverage Overview

| Type | Date | Line % | Branch % | Report |
|------|------|--------|----------|--------|
| <UT> | <YYYY-MM-DD> | <percent>% | <percent>% | [report](<layer>/coverage/) |

## How to Use

- **Find test cases by date**: Browse the "Recent Generations" table and click the linked spec documents
- **Find test cases by code**: Search within spec documents for Target Class or Target Method
- **Check coverage trends**: Compare Coverage Overview rows across dates
- **Avoid duplicates**: Before generating new tests, scan existing spec docs to see what's already covered

## Notes

- Each spec document is independently versioned (see frontmatter `version` field)
- Spec documents with the same date and test type are merged (not duplicated)
- Coverage reports are linked relative to this file's directory
- Only test types that have been executed appear in this index
```

**Important**: When updating the wizard in subsequent runs with different test types, ADD rows for the new type — never remove existing rows for other types. The wizard accumulates entries across all test types over time.

### Step 7: Confirm

Log a confirmation:
```
✓ Spec doc generated: docs/khufu/<layer>/<YYYY-MM-DD>-<layer>-test-cases.md (version <N>)
✓ Wizard updated: docs/khufu/test-cases.md (version <N>)
```

## Spec Document Update/Merge Logic

When merging new test cases into an existing spec doc (same date, same layer):

### Dedup Rule
Two test cases are considered the same if **both** match:
1. Same `Test Class` (normalized: trim whitespace, unify backticks)
2. Same `Test Method` (normalized: trim whitespace, unify backticks)

When a match is found:
- Keep the **existing** test case in its current position (preserve row number)
- Update its `Status` to the **latest** result (may change from ❌ to ✅ if fixed)
- Do NOT add a duplicate row

When no match is found:
- Append the new test case with the next available row number

### Recalculation After Merge
- `Total test cases`: count of all unique rows
- `Passed`: count of rows with Status = ✅
- `Failed`: count of rows with Status = ❌
- `Skipped`: count of rows with Status = ⏭️
- Coverage statistics: always use the LATEST data (coverage tools measure current state, not incremental)

## Version Metadata Convention

### Spec Doc Frontmatter
```yaml
---
version: 3              # Increments each time this spec doc is updated
created: 2026-07-13      # First creation date (never changes)
updated: 2026-07-13T15:30:00+08:00  # Last update time (always changes)
testType: ut             # One of: ut, it, api, e2e
language: c++            # Detected language
tool: Google Test 1.14.0 # Framework + version
coverageTool: gcov + lcov 2.0  # Coverage tool + version
---
```

### Wizard File Frontmatter
```yaml
---
version: 5              # Increments each time the wizard is updated
created: 2026-07-10      # First creation date
updated: 2026-07-13T15:30:00+08:00  # Last update time
---
```

## Timestamp Generation

Use the `date` command to get the current ISO 8601 timestamp:
```bash
date -u +"%Y-%m-%dT%H:%M:%SZ"  # UTC
# or
date +"%Y-%m-%dT%H:%M:%S%z"    # With timezone offset
```
